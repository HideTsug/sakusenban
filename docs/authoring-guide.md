# 作戦盤オーサリングガイド（AI向け・自己完結）

このガイドだけで、AI が作戦盤（展開式スイムレーンタスク盤）を作成・更新できる。前提知識・会話文脈は不要。

## 作戦盤とは

複数の実行主体（人間・AI・相手側の人間/AI）が絡む仕事の段取りを、レーン別・依存順の「箱」に落とした業務フロー盤。各箱を開くと手順チェックリスト・完了条件・タスクリンクが出る。1枚のHTMLで、開いた人がチャット履歴を遡らずに動ける。

## 設計思想（4原則）

1. **盤は生成ビュー、正本は外部SSoT**（GitHub Issues または state.json）。盤の手編集は禁止。状態が変わったら正本を更新→盤を再生成する。チェックボックスは端末ローカル（localStorage）の作業メモであり、完了の正本はタスクのクローズ
2. **開いた瞬間に動ける**ことが価値。箱のタイトルだけで流れを掴み、開くと「▸ 最初にやること1行」→手順チェック→完了条件（機械検証コマンド付き）まで自己完結で書く
3. **人間の実行とAIの実行をレーンで分離**する。人間レーンの箱 = 人間にしかできないこと（判断・署名・実機操作・相手との対話）だけに絞る。AIができることを人間レーンに置いたら設計ミス
4. **チェック→報告→反映のループ**が盤を生かす。下部バーの「報告をコピー」が `[<盤名>チェック報告 v1]` 形式のテキストを吐き、利用者がそれをAIに貼る→AIが正本を検証・更新し盤を再生成する

## 作成手順

### 1. 真実収集（捏造タスク禁止）

- タスク・状態・依存は必ず情報源から取る（`gh issue list` / `gh issue view N --comments` / プロジェクト文書）
- 盤に載せる各タスクに出典（issue #N 等）を付ける。出典のないタスクを発明しない
- ボール所在（今誰の番か）は記録の往復から実測する

### 2. 構造設計

- **レーン** = 実行主体（1〜6）。kind は human（青）/ ai（灰）/ joint（橙）
- **ストリーム** = 並行して進む仕事の束。ストリームごとにグリッドが分かれ、使うレーンだけが描画される
- **箱** = 1回の「ボール保持」単位（同じ主体が連続してやる作業のまとまり）。依存順に上から並べ、connector 矢印でボールの受け渡しを表す
- **タスク** = 箱の中身。4欄: ゴール / 手順（steps）/ 完了条件（accepts・機械検証コマンド付き）/ 依存（deps）
- **束（bundle）** = 人間キュー。同質作業（ブラウザ作業・外出・署名会）をまとめ、1回の腰上げで消化できる単位にする
- **状態は書かない**。ready/blocked/done は renderer が state.json と deps から導出する
- **issue を立てない人間・AI ステップ**（本人が質問に答える・PC を起動する・承認する等）は、合成 id（例 9001〜）の task に `link: false`（番号を issue にリンクしない）と `display: "承認1"`（`#N` の代わりに表示する短い名札）を付けて置く。state.json に同じ number の row（title・state）を持たせる。運用規約が「手順分解で issue を増やさない」場合の受け皿で、正本は隣接する issue 側（`next_action` に根拠 issue を書く）。チェック報告・localStorage キーは従来どおり数値 id を使う（`examples/board.yaml` の task 9001 が実例）

#### 分岐・戻り・条件付きの箱

`flow.streams[].boxes[]` に経路を記述する。ストリーム内に `next` または `optional` があれば、分岐対応のグリッドで描画する。

| 構文 | 型・意味 |
|---|---|
| `next: [{to: r3, label: "承認"}]` | 配列。この箱の全出線を指定し、既定の線を置き換える。`next: []` は出線なし |
| `next[].to` | 必須の文字列。同一ストリーム内の箱 key。自箱や他ストリームの箱は指定不可 |
| `next[].label` | 文字列。出線が2本以上なら全出線に空白だけでないラベルが必須。1本なら任意。24文字以内を推奨し、超過は警告 |
| `next[].kind: alt` | 任意。指定できる値は `alt` のみで、例外経路を破線で表す |
| `optional: true` | boolean（省略時は false）。条件付きの箱。既定の線はこの箱を飛ばす。先頭の箱には true を指定不可 |

```yaml
boxes:
  - key: r1
    lane: lead
    name: "承認・差し戻し判断"
    next:
      - {to: r3, label: "承認"}
      - {to: r2, label: "差し戻し", kind: alt}
  - key: r2
    lane: ai
    name: "訂正・再申請"
    optional: true
    next: [{to: r1, label: "再申請"}]
  - {key: r3, lane: lead, name: "承認済処理"}
```

- `next` を省略した箱は、後続の `optional: true` の箱を連続して飛ばし、最初の optional でない箱へ無ラベルの1本を持つ。該当する箱がなければ出線なし。明示した `next` は optional の箱も行き先にできる
- 辺の種別は箱の並び順から導出する。既定の行き先（optional を飛ばした次の箱）への辺は `main`、それ以外の後方への辺は `skip`、前方への辺は `return`。`kind: alt` はこの種別を変えない
- 分岐は複数の出線、合流は複数の辺が同じ箱を指すことで表す。判断ひし形や合流専用の構文は作らず、箱 = 1回のボール保持を守る
- 参照・ラベル必須・型・先頭 optional の違反は検証エラー。先頭以外で入線ゼロ、先頭から前進辺（main/skip）だけでは到達できない箱、24文字を超えるラベルは `render.py: warning: …` と stderr に警告する。戻り辺からの入線があっても前進到達性は別に検証する
- **`deps` とは独立**。辺から deps を生成せず、戻り辺でタスクを再オープンせず、飛ばした箱を done にしない。着手可否と完了は引き続き deps と state.json だけで決まる
- **分岐箱には「それ以外」の出口を必ず 1 本書く**（BPMN のデフォルトフロー相当）。これは作成規約であり、validate では強制しない
- **配色・フラットデザイン規範は不変**。graph の線（connector・edge・stem）は `--line-strong` 1色・2pxに統一し、矢印も同じ大きさにする。通常（main と skip）は実線、例外（kind: alt）は破線（6 4）、戻り（return）は点線（2 3、alt でも戻りを優先）。graph のヘッダ凡例は「実線=通常／破線=例外／点線=戻り／分岐 N=出口が複数ある箱」。optional は破線枠と「条件付き」で表す
- 出線2本以上、または1本でも飛ばし・alt・戻りがある箱には、直下に出口行を置く。隣接 main → 前進群（skip/alt を跨ぐ区間長の降順）→ 戻り群（区間長の昇順）で「条件 → 番号 箱名」を並べ、同点は登場順を保つ。高さ22px・24pxピッチ、箱名は14文字までの単行省略。戻りは ↩、例外は ⇢ で示す
- 出口行を持つ箱の隣接 main は、該当する出口チップの中心から本文行を跨ぐ縦線（stem）で通路行の connector に繋ぐ。線上ラベルは出口行を持たない箱の隣接 main にだけ表示し、出口チップとの重複を避ける
- 出線2本以上の boxmeta に「分岐 N」を表示する。出口行を持つ箱の本文先頭には「出口」の全文一覧（条件・種別・行き先）を置く。ラベル付きの単一隣接 main は出口行を増やさず、本文の一覧にその1本の全文を残す。出口リンクはキーボード／タップで既存の `data-open-box` ハンドラが目標箱を開く
- 飛ばし・alt は出口行の右辺から右レール、戻りは左辺から左レールを通る。optional を飛ばす main も前進群に含め、描画分類は route=skip（通常は実線、kind: alt は破線）とする。到着側はラベルを置かず8px間隔で合流して矢印1本へ束ね、隣接 connector のラベルだけ水平線の上に残す。同じ出発箱・行き先のレール線は出口と逆順に到着させる。本文を開いてもCSSグリッドに追従する
- レール番号は内側から数え、重ならない区間で再利用し、短い区間から内側に割り当てる。同じ出発箱の線の非交差を優先し、前進（右・下向き）は上の出口ほど外側、戻り（左・上向き）は下の出口ほど外側にする。出口の長さ順と合わせ、長辺ほど外側になる。同長でも出口の登場順を保って交差を避け、割り当てを決定的にする
- graph を含む本文は最大1280px。各レーンに最小13remと左右レール幅を確保し、狭い画面では盤内を横スクロールする。`:has` 非対応ブラウザの本文は従来の960pxのまま
- `next` も `optional` もないストリームの DOM・従来盤の凡例は不変。`check_board.py` は箱行のセル数・同一グリッド内の辺参照と出口リンク・connector 幾何を検査する。印刷のページ跨ぎで線が切れる制限は残り、出口の文字とリンクで補う

### 3. 出口を先に決める（骨格の有無が変わる）

盤の出口は2つあり、**必要な HTML の形が違う**。生成の前にどちらか決めること。

| 出口 | 必要な形 | renderer の指定 |
|---|---|---|
| **file:// / ローカル配信 / 添付** | 完全な文書骨格（`<!doctype html>` / `<html lang>` / `<head>` / `<meta charset>` / `<body>`） | 既定（オプションなし） |
| **Artifact 公開** | 骨格なしの断片（`<title>` 以降のみ） | `--fragment` |

Artifact は公開時にファイルを `<!doctype html>…<head>…</head><body>` でラップするため、投入するファイル側に doctype / html / head / body を書くと**入れ子の不正な文書**になる。charset もホスト側の head が供給するので断片側には不要。

逆に file:// で開く盤に骨格がないと、`<meta charset>` がないため日本語が文字化けする。骨格ありの盤では charset を先頭 1024 バイト以内に置く必要がある（HTML 仕様のエンコーディング宣言の制限）。renderer は既定でこれを満たす。

### 4. 生成（2経路）

**経路A: renderer（推奨・構造化されたプロジェクト向け）**

```bash
# 構造: board.yaml（schema/sakusenban.schema.json 準拠）
# 状態: GitHub Issues なら
gh issue list --state all -L 200 --json number,title,state > state.json
# GitHub を使わないなら state.json を手で維持（同じ形式）

# file:// / ローカル配信向け（完全な文書骨格つき）
python3 scripts/render.py board.yaml state.json > board.html

# Artifact 公開向け（骨格なし断片）
python3 scripts/render.py board.yaml state.json --fragment > board-artifact.html
```

**経路B: 手書き（1回きりのセッション盤向け）**

見本を**別名にコピーしてから**、そのコピーの CSS/JS 機構をそのまま流用してコンテンツを差し替える（`templates/` 配下は renderer の生成物で `scripts/check.sh` が鮮度を検証しているため、直接編集しない）。コピー元は出口で選ぶ: **Artifact 公開なら `templates/fragment.html`**（骨格なし）、**file:// / ローカル配信なら `templates/template.html`**（骨格あり）。ここを間違えると、Artifact では骨格が入れ子になり、file:// では文字化けする。変更必須: `<title>` / h1 / JS の `KEY`（盤ごと一意）と `REPORT_HEAD`。connector の百分率: レーン i（0始まり）の中心 = `(i+0.5)/レーン数*100`

手書き経路での注意（renderer 経路では自動的に守られる）:

- **差し替える範囲は `<main>` の直後から `<div class="syncbar"` の直前まで**。`<style>`・`syncbar`・`<script>` は触らない。この境界で切ると CSS/JS 機構を1文字も壊さずに本文だけ入れ替えられる（配布先での実走で確認）
- **生成は一時スクリプトファイル経由で行う**。HTML をシェルのヒアドキュメントに直接埋めるとクォートが壊れて生成に失敗する（同実走で確認）
- **`KEY` と `REPORT_HEAD` にシングルクォート・`</script>`・バックスラッシュを含めない**。どちらも JS の単引用符リテラルに直接埋まるため、盤名に `'` が入ると構文が壊れ、`</script>` が入るとスクリプトが途中で終了する。`REPORT_HEAD` には盤名を必ず入れる規約（下記）があるので、盤名の側でこれらの文字を避ける
- **`REPORT_HEAD` には盤名を必ず入れる** — `[<盤名>チェック報告 v1] ` 形式。報告を受け取る側は、この見出しで「どの盤の報告か」を特定する。複数の盤を並行運用すると、盤名がないと report がどれに属するか判別できない
- **正本で完了を確認済みのステップ**は、input に `checked disabled` を付けたうえで、その `label.ck` に `.ssot-done` を付ける（緑チェック＋緑の取り消し線）。`.ssot-done` を落とすと通常の減光表示になり、「端末ローカルでチェックしただけ」と「正本で確認済み」が見分けられなくなる
- **blocked 手順への `disabled` は盤の寿命で使い分ける** — 数日〜数週間スパンの盤は付ける（未着手タスクの誤チェック防止）／一座の同席セッション盤は付けない（依存が順に消化される前提で、盤を再生成せずライブで打鍵する方が価値が高い）

### 5. 配色規範（重要・逸脱禁止）

色は**意味にのみ**付与する: 青=人間の実行と押せる操作（塗り=操作 / 淡色=状態で区別）/ 橙=共同・注意 / 緑=着手可・OK・正本確認済み / 赤=期限切迫 / グレーアウト＋タイトル取り消し線=完了（減光だけでは環境により判別しにくいため両方付く）。端末ローカルのチェックは青塗り、正本確認済み（`.ssot-done`）のチェックは緑塗りで描画される。レーン背景・番号バッジ・装飾への色付与は禁止。新しい色を足すのは新しい「意味」ができた時だけ。

実値は**デジタル庁デザインシステム（DADS）のデザイントークン**に準拠する（キーカラー #0017C1 = Blue-900、出典: `digital-go-jp/design-tokens` v2。`assets/style.css` が唯一の正本）。フラットデザインを守ること: ドロップシャドウ・グラデーション・hover での浮上を足さない。角丸は 8px（小要素 4px）まで。ダークモードは DADS 非対応のため sakusenban 独自拡張（DADS のグレースケール・色相スケールから導出）。

### 6. チェック報告の受け方（AI側プロトコル）

利用者が `[<盤名>チェック報告 v1]` を貼ってきたら:

1. 各項目を**正本で検証してから**反映する（issue コメント/クローズ、ファイル存在確認等）。検証なしに「反映しました」と言わない
2. 反映後に盤を再生成する（正本で完了確認済みのステップは `checked disabled` + `.ssot-done` で描画される — renderer 経路なら自動）
3. 実施済みと聞いただけで未検証のものはチェック済みにしない

## 品質チェック（発行前）

- [ ] 全タスクに出典がある
- [ ] ready/blocked が依存関係と整合（`scripts/render.py` の validate が機械検証する）
- [ ] 人間レーンの箱に「AIで代替可能な作業」が混ざっていない
- [ ] 完了条件がすべて機械検証可能（コマンド or 観測可能な事実）
- [ ] `bash scripts/check.sh` が OK
- [ ] graph の出口行数が対象条件と一致（同梱 examples は1行。下記コマンドで確認）。生成HTMLの grid-row/grid-column・出口インデックス `k`・`data-rail` から、同じ箱の前進レール線は `k` が小さいほど外側、戻りは `k` が大きいほど外側で、出発側・到着側とも交差しないことを確認する
- [ ] 手書き経路の生成物は `python3 scripts/check_board.py <盤.html>` が OK（レーン数・各行セル数・connector 位置の機械検証。renderer 経路は validate() が担う）

```bash
python3 scripts/render.py examples/board.yaml examples/state.json > /tmp/sakusenban-example.html
grep -o 'class="exitcell"' /tmp/sakusenban-example.html | wc -l
# Expected: 1 (the branch at r3)
```

生成HTMLでは同じ行に複数の出口行要素が並ぶため、`grep -c` の一致行数ではなく、`grep -o` と `wc -l` で要素の出現数を数える。

## 運用の使い分け

- **数日〜数週間スパンの盤**: blocked 手順は disabled（未着手タスクの誤チェック防止）— renderer の既定挙動
- **一座のセッション同席盤**（2時間枠等）: 依存は順に消化される前提で全チェックを有効にし、盤を再生成せずライブで打鍵する方が価値が高い。手書き経路で disabled を外す
